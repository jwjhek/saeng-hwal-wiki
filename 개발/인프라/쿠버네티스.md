# 쿠버네티스

> **분류:** 개발 › 인프라 · [[생활위키 목차]]

쿠버네티스(Kubernetes, **K8s**)는 컨테이너를 **여러 머신**에 나눠 올리고, 죽으면 다시 띄우고, 트래픽을 나누고, 설정을 주입하는 **오케스트레이션** 플랫폼이다. 
[[Docker 사용법]]이 “한 상자(컨테이너)를 만드는 법”이라면, K8s는 “상자를 **공장·물류**처럼 운영하는 법”에 가깝다.

공식: [https://kubernetes.io](https://kubernetes.io) 
문서: [https://kubernetes.io/docs/](https://kubernetes.io/docs/)

확인일: 2026-08-06 
로컬 실습은 **minikube / kind / Docker Desktop Kubernetes / k3d** 중 하나로 충분하다.

---

## 1. 쓰는 이유

| Docker만으로 | K8s가 돕는 지점 |
|--------------|-----------------|
| 한 호스트 Compose | 여러 노드에 분산 배치 |
| 컨테이너 죽으면 수동/재시작 정책 | Desired state — 원하는 개수 유지 |
| 롤링 배포·헬스체크를 직접 | Deployment·Probe로 표준화 |
| 서비스 디스커버리를 Compose 네트워크 | Service / DNS |
| 시크릿·설정을 파일로 관리 | ConfigMap / Secret |
| 오토스케일 직접 | HPA 등 |

혼자 쓰는 작은 앱·로컬 DB는 Compose로도 충분하다. 
**여러 서비스·무중단 배포·다중 노드·팀 공통 운영**이면 K8s를 검토한다.

```text
개발자 → 이미지 빌드 (Docker)
 → 매니페스트/Helm 적용
클러스터 → Pod를 노드에 배치 · 재시작 · 로드밸런스
```

---

## 2. 핵심 개념

| 용어 | 의미 |
|------|------|
| **클러스터 (Cluster)** | 마스터(컨트롤 플레인) + 워커 노드 집합 |
| **노드 (Node)** | 컨테이너가 실제로 도는 머신 (VM/베어메탈) |
| **Pod** | 스케줄 최소 단위. 보통 컨테이너 1개(+사이드카) |
| **Deployment** | Pod의 복제본 수·롤링 업데이트 선언 |
| **ReplicaSet** | Deployment가 관리하는 “N개 유지” |
| **Service** | Pod들에 안정적인 가상 IP·DNS 이름 |
| **Ingress** | HTTP(S) 진입점 (도메인·경로 라우팅) |
| **Namespace** | 논리 격리 (`dev`, `prod` …) |
| **ConfigMap / Secret** | 설정·민감 정보 주입 |
| **Volume / PVC** | 디스크·영속 볼륨 청구 |
| **kubectl** | 클러스터 CLI |

```text
Deployment
 └── ReplicaSet
 └── Pod(s) ←── Service(클러스터IP/DNS)
 ↑
 Ingress (외부 HTTP)
```

컨트롤 플레인:

- **API Server** — 모든 요청의 관문 
- **etcd** — 클러스터 상태 저장 
- **Scheduler** — Pod를 어느 노드에 둘지 
- **Controller Manager** — Desired vs Actual 맞추기 

워커: **kubelet**, **kube-proxy**, 컨테이너 런타임(containerd 등).

---

## 3. Docker와의 관계

| | Docker | Kubernetes |
|--|--------|-------------|
| 단위 | 이미지·컨테이너 | Pod·워크로드 API |
| 범위 | 주로 한 머신 / Compose | 클러스터 |
| 선언 | Dockerfile, compose.yml | YAML 매니페스트, Helm |
| 런타임 | dockerd 등 | 보통 containerd (Docker 엔진 필수 아님) |

이미지는 그대로 쓴다. 
`docker build` → 레지스트리 push → Deployment `image:` 에 태그 지정.

구식 표현 “Docker를 K8s에 올린다”보다 **“OCI 이미지를 K8s가 돌린다”**가 정확하다.

## 5. 첫 배포 흐름

### 5.1 Deployment + Service (예: nginx)

`nginx-deploy.yaml` 예시:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
 name: web
spec:
 replicas: 2
 selector:
 matchLabels:
 app: web
 template:
 metadata:
 labels:
 app: web
 spec:
 containers:
 - name: nginx
 image: nginx:alpine
 ports:
 - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
 name: web
spec:
 selector:
 app: web
 ports:
 - port: 80
 targetPort: 80
 type: ClusterIP
```

```bash
kubectl apply -f nginx-deploy.yaml
kubectl get deploy,po,svc
kubectl rollout status deploy/web
```

로컬에서 브라우저로 보려면:

```bash
kubectl port-forward svc/web 8080:80
# http://localhost:8080
```

또는 Service `type: NodePort` / `LoadBalancer`(클라우드·Desktop에서 지원 시).

### 5.2 자주 쓰는 kubectl

```bash
kubectl apply -f app.yaml # 선언 적용 (권장)
kubectl delete -f app.yaml
kubectl get pods -o wide
kubectl describe pod <이름> # 이벤트·원인
kubectl logs <pod> [-c 컨테이너]
kubectl logs -f deploy/web # 팔로우
kubectl exec -it <pod> -- sh
kubectl scale deploy/web --replicas=3
kubectl rollout undo deploy/web
kubectl config get-contexts # 클러스터 전환
```

디버그: **Pending → describe(이벤트) → ImagePull / 리소스 / Affinity**. 
CrashLoop: **logs → 설정·포트·헬스체크**.

## 6. 설정·시크릿·스토리지

### ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
 name: app-config
data:
 APP_ENV: "dev"
```

Pod에서 `envFrom` / 볼륨 마운트로 주입.

### Secret

Base64(또는 문자열 리터럴 `stringData`). 
Git에 평문 Secret 커밋 금지 → **Sealed Secrets / External Secrets / 클라우드 시크릿 매니저** 검토.

### 볼륨

| 종류 | 용도 |
|------|------|
| emptyDir | Pod 생명주기 임시 |
| PVC + StorageClass | DB 등 영속 (클라우드 디스크, local-path 등) |
| hostPath | 로컬 실습용 (프로덕션 비권장) |

상태가 있는 앱(DB)은 **StatefulSet + PVC** 패턴을 따로 배운다. 웹 API는 Deployment가 기본.

## 7. 네트워크

| 리소스 | 역할 |
|--------|------|
| **ClusterIP** | 클러스터 내부만 (기본) |
| **NodePort** | 노드 IP:포트로 노출 |
| **LoadBalancer** | 클라우드 LB 연동 |
| **Ingress** | `/api`, `app.example.com` 등 HTTP 라우팅 |
| **NetworkPolicy** | Pod 간 허용/차단 (CNI 지원 필요) |

서비스 디스커버리: 같은 네임스페이스면 `http://web:80`, 
다른 NS면 `web.다른ns.svc.cluster.local`.

## 8. 헬스체크·리소스·스케일

### Probe

| Probe | 질문 |
|-------|------|
| **liveness** | 죽었나? → 재시작 |
| **readiness** | 트래픽 받을 준비됐나? → Service에서 제외 |
| **startup** | 기동 느린 앱용 |

잘못된 liveness는 **재시작 루프**를 만든다. readiness와 역할을 섞지 말 것.

### resources

```yaml
resources:
 requests:
 cpu: "100m"
 memory: "128Mi"
 limits:
 cpu: "500m"
 memory: "256Mi"
```

`requests`는 스케줄링 기준, `limits`는 상한. 
비우면 노드 자원을 과점할 수 있다.

### HPA

CPU/메모리(또는 커스텀 메트릭) 기준으로 Deployment 복제본 자동 증감. 
메트릭 서버가 클러스터에 있어야 한다.

## 9. 배포 방식과 GitOps

| 방식 | 내용 |
|------|------|
| `kubectl apply` | 파일·폴더 직접 |
| **Helm** | 차트·값으로 패키징 (`values.yaml`) |
| **Kustomize** | 베이스 + 오버레이 (kubectl 내장) |
| **Argo CD / Flux** | Git 상태가 클러스터 상태 (GitOps) |

실무 흐름 예:

```text
CI: 테스트 → 이미지 빌드 → 레지스트리 push → 태그 갱신
CD: Helm/Argo가 새 태그로 롤아웃
```

이미지 태그는 `:latest`만 쓰지 말고 **버전·digest**를 고정하는 편이 안전하다.

## 10. 네임스페이스·RBAC·보안 최소

1. `dev` / `staging` / `prod` 네임스페이스 분리 
2. 서비스 계정(ServiceAccount) + **RBAC** — 최소 권한 
3. 이미지는 신뢰 레지스트리, 가능하면 스캔 
4. 컨테이너 **root 비권장**, readOnlyRootFilesystem 등 Pod Security 
5. Secret은 etcd·백업·RBAC까지 생각 
6. API Server는 공개망에 직접 노출하지 않기 

클라우드: EKS / GKE / AKS 는 컨트롤 플레인을 관리형으로 준다. 
온프레: kubeadm, k3s, OpenShift 등.

## 11. Spring·Java와의 연결

[[Spring과 Spring Boot 학습]] 앱을 컨테이너화한 뒤:

1. Dockerfile로 JAR 이미지 ([[Docker 사용법]]) 
2. Deployment + Service + (선택) Ingress 
3. `SPRING_PROFILES_ACTIVE`, DB URL은 ConfigMap/Secret 
4. readiness: `/actuator/health` 등 
5. 롤링 업데이트 시 그레이스풀 셧다운(`terminationGracePeriodSeconds`) 

로컬은 Compose, 공용/운영은 K8s로 나누는 팀이 많다.

## 13. 자주 하는 실수

| 실수 | 대안 |
|------|------|
| latest만 배포 | 불변 태그·digest |
| Secret을 Git에 | 암호화·외부 시크릿 |
| liveness로 외부 의존 체크 | readiness / 앱 설계 분리 |
| requests 없이 과밀 | requests·limits·쿼터 |
| 한 Pod에 너무 많은 책임 | 서비스 단위로 쪼개기 |
| 로컬 hostPath를 운영에 | PVC·클라우드 디스크 |
| apply만 하고 describe 안 봄 | 이벤트·로그가 1순위 |

## 14. 치트시트

```bash
# 컨텍스트
kubectl config current-context
kubectl config use-context <이름>

# 상태
kubectl get deploy,po,svc,ingress -n <ns>
kubectl top nodes # metrics-server 필요
kubectl top pods -n <ns>

# 적용·차이
kubectl apply -f . --dry-run=client -o yaml
kubectl diff -f app.yaml

# 문제
kubectl get events -n <ns> --sort-by=.lastTimestamp
kubectl describe po <pod>
```

YAML 필드가 기억 안 나면:

```bash
kubectl explain deployment.spec.template.spec.containers
```
