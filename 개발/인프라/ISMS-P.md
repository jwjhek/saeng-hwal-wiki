# ISMS-P

> **분류:** 개발 › 인프라 · [[생활위키 목차]]

**ISMS-P**(정보보호 및 개인정보보호 관리체계 인증)는 조직이 정보보호·개인정보보호를 위해 갖춘 **관리체계**가 국가 **인증기준**에 맞는지 **KISA(한국인터넷진흥원)** 등이 심사해 증명하는 제도다.

말할 때 **「ISMP」** 로 줄여 부르는 경우가 있으나, 공식 명칭은 **ISMS-P** 이다. **ISMS**만 쓰면 **개인정보 영역 없이** 정보보호만 인증한 형태를 가리키는 경우가 많다.

공식: [ISMS-P 인증 (KISA)](https://isms.kisa.or.kr/) · [isms-p.or.kr](https://www.isms-p.or.kr/)  
확인일: 2026-08-11

관련: [[전자정부프레임워크]] · [[Spring과 Spring Boot 학습]] · [[Git 사용법]] · [[Docker 사용법]] · [[클라우드 AWS GCP Azure]]

## 1. 개요

| 항목 | 설명 |
|------|------|
| 무엇 | **정보보호 + 개인정보보호** 관리체계 **인증** (통합 인증) |
| 누가 | **기업·기관** (개인이 따로 받는 인증 아님) |
| 왜 | 법적 **의무**, 입찰·계약 요건, 고객 **신뢰**, 사고 **리스크** 감소 |
| 이전 | **PIMS**(개인정보) + **ISMS**(정보보호)가 **2018년**부터 **ISMS-P**로 통합 |

```text
정책·조직·위험관리 (관리체계)
        +
기술·운영 보호대책 (접근통제·암호화·로그·백업 …)
        +
개인정보 처리단계별 조치 (수집·이용·파기 …)
        ↓
   심사·증적 → 인증서 (유효기간·사후심사)
```

개발자는 **「인증 받자」** 보다 **로그·권한·배포·취약점** 요구가 일상 업무에 **걸리는지**를 먼저 본다.

---

## 2. ISMS vs ISMS-P

| 구분 | ISMS | ISMS-P |
|------|------|--------|
| 영역 | **정보보호** 관리체계 | 정보보호 **+ 개인정보** 처리 |
| 기준 수 | **80개** 항목 (1·2영역) | **101개** 항목 (1·2·**3**영역) |
| 언제 | 의무 대상 중 **정보보호만** 최소 충족 등 | **개인정보**를 다량 처리·의무 대상이 **통합**인 경우가 많음 |
| 관계 | ISMS-P는 ISMS **확장** 형태로 이해하면 편함 |

**개인정보**를 서비스 핵심으로 다루면 실무에서는 **ISMS-P** 를 목표로 잡는 경우가 많다. 
법·고시·의무 대상은 **연도·업종**마다 바뀌므로 공식 안내가 최종본이다.

---

## 3. 인증기준 구조 (101개)

크게 **3개 영역**이다. (세부 항목·번호는 개정될 수 있음)

| 영역 | 항목 수 | 다루는 것 |
|------|---------|-----------|
| **1. 관리체계 수립·운영** | 16 | 정책, **CISO·CPO** 등 책임, 위험관리, 내부점검·개선 |
| **2. 보호대책 요구사항** | 64 | 조직·인적·물리 보안, **인증·권한**, 접근통제, **암호화**, 개발·운영·사고대응·**재해복구** |
| **3. 개인정보 처리단계별** | 21 | 수집·이용·**제공·위탁**·파기, 정보주체 권리 |

개발·운영과 직접 맞닿는 예:

- 계정 **최소 권한**, 퇴사 시 **권한 회수**  
- **로그** 보관·위변조 방지  
- **취약점** 점검·패치  
- **개발·테스트·운영** 환경 분리  
- **백업·복구** 절차  
- 개인정보 **마스킹·암호화**  

[[전자정부프레임워크]]·[[Spring과 Spring Boot 학습]] 의 보안·권한 설계와 **겹치는 축**이 있다.

## 4. 인증체계 (역할)

| 역할 | 예 |
|------|-----|
| **정책기관** | 과학기술정보통신부, **개인정보보호위원회** |
| **인증기관** | **KISA**, 금융권 **금융보안원** 등 |
| **심사기관** | KAIT, TTA, OPA, NISC 등 (지정 기관) |
| **신청 주체** | 인증 받는 **사업자·기관** |

인증서·로고 사용·범위는 **인증 범위(시스템·서비스)** 문구를 따른다.

---

## 5. 의무 대상 (참고)

**반드시 해당한다**고 단정하지 말고, **매출·이용자 수·업종·법 개정**으로 갈린다. 
아래는 **자주 거론되는 축**이다.

| 예시 (유형) | 요지 |
|-------------|------|
| 정보통신서비스 제공자 | 일정 **매출·이용자** 기준 |
| 일정 규모 **병원** | 의무 대상으로 논의되는 경우 |
| 일정 규모 **학교** | 재학생 수 등 |
| **가상자산** 사업자 | 별도 의무 논의 |
| 그 외 | **자발적** 인증 (입찰·B2B 요구) |

미이행 시 **과태료** 등 제재가 붙을 수 있다. 
해당 여부는 **법무·컴플라이언스**·공식 FAQ로 확인한다.

## 6. 심사 종류·주기

| 심사 | 목적 |
|------|------|
| **최초심사** | 처음 인증 — 보통 **유효기간 3년** |
| **사후심사** | 유지 여부 — **연 1회 이상** 등 |
| **갱신심사** | 만료 전 **재인증** |

심사는 **문서(정책·지침)** 와 **증적(로그·기록·회의록)** 을 본다. 
「정책만 있고 운영 안 함」이면 **결함**이 난다.

---

## 7. 준비 흐름 (조직 관점)

```text
1) 범위 정의 — 어떤 서비스·시스템을 인증에 넣을지
2) 갭 분석 — 기준 101개 대비 현황
3) 정책·지침·조직 — CISO/CPO, 위험평가
4) 기술 조치 — 접근통제, 로그, 암호화, 백업, SDLC
5) 증적 축적 — 최소 수 주~수 개월 **실제 운영** 기록
6) 심사 신청 — 인증기관·심사기관 계약
7) 결함 보완 — 보완조치내역서
8) 인증 유지 — 사후심사 대비
```

컨설팅·도구 없이도 가능하지만, **인력·기간**이 많이 든다. 
실무에서는 **6개월 이상** 여유를 두는 안내가 흔하다.

## 8. 개발자가 체감하는 것

인증 **프로젝트**에 끼우지 않아도, 인증 받은 회사에서는 아래가 **일상**이 될 수 있다.

| 요구 | 개발 쪽 예 |
|------|------------|
| 접근통제 | 운영 DB·서버 **개인 계정**, 공용 계정 금지 |
| 로그 | 로그인·권한 변경·중요 조회 **기록** |
| 변경관리 | 배포 **승인·이력**, [[Git 사용법]]·[[GitHub]] PR |
| 취약점 | 정기 **점검·패치**, 오래된 라이브러리 |
| 개인정보 | 로그에 **주민번호·전화** 넣지 않기, 마스킹 |
| 백업 | DB·설정 **복구 테스트** |
| 사고 | 유출 의심 시 **보고** 절차 |

「빨리 배포」와 충돌할 수 있어, **예외 절차**가 문서로 있어야 한다.

## 9. 헷갈리기 쉬운 것

| 이름 | ISMS-P와 관계 |
|------|----------------|
| **CSAP** | **클라우드 서비스** 보안 인증. 조직 ISMS-P **대체 아님** |
| **ISO 27001** | 국제 **정보보안** 표준. 국내 **법적 의무 인증**과 별개. 병행·연계 사례는 있음 |
| **ISO 27701** | 개인정보 **확장**. ISMS-P와 **목적·심사 체계**가 다름 |
| **개인정보 처리방침** | 웹에 올리는 **고지** 문서. ISMS-P **전체**가 아님 |

「클라우드 쓰니까 CSAP면 된다」·「ISO 있으면 ISMS-P 면제」 식 **단순화**는 위험하다.
