# 바이브 코딩

> **분류:** AI · [[생활위키 목차]]

**바이브 코딩**(vibe coding)은 2025년 **안드레이 카파시**(Andrej Karpathy)가 소개한 말로, **자연어로 원하는 결과를 말하고** LLM·AI 에이전트가 **코드를 대신 쓰게** 두는 개발 방식이다. 
극단적인 형태에서는 **diff를 읽지 않고**, 에러 메시지를 **그대로 붙여 넣어** 고치게 하며, “코드가 있다는 사실을 잊는” 쪽에 가깝다.

이 글은 **개념·스펙트럼·적합한 상황·위험**을 정리한다. [[Cursor 사용법]]·[[GitHub Copilot 사용법]]을 쓰는 것과 **같지 않다** — 도구는 같아도 **얼마나 검수하느냐**가 갈린다.

확인일: 2026-08-11

관련: [[Cursor 사용법]] · [[GitHub Copilot 사용법]] · [[현존 AI 비교]] · [[LLM Wiki]] · [[디자인 패턴]]

---

## 1. 개요

| 항목 | 설명 |
|------|------|
| 누가 | 카파시(전 OpenAI·Tesla AI)가 **2025년 2월** X(트위터)에 올린 글에서 유행 |
| 한 줄 | “**바이브에 맡기고**, 지수적으로 AI를 믿으며, **코드 존재를 잊는다**” |
| 도구 예 | [[Cursor 사용법]] Composer·Agent, ChatGPT, Claude, [[GitHub Copilot 사용법]] |
| 전제 | LLM이 **충분히 좋아져서** “말만 하면 대부분 돌아간다”는 체감 |

```text
의도·화면·느낌을 말함
 ↓
AI가 코드 생성·수정
 ↓
실행해 보고 (diff는 안 읽어도 됨 — 극단형)
 ↓
에러 나오면 메시지를 AI에 붙여 넣기
 ↓
“대충 되면” 다음 기능
```

카파시 본인은 **주말용·버릴 프로젝트**에 가깝다고도 했다. **회사 핵심 서비스**에 그대로 옮기면 위험하다.

---

## 2. 카파시가 말한 방식 (요지)

원문 요지만 옮긴다. **농담·실험 톤**이 섞여 있다.

| 습관 | 내용 |
|------|------|
| 입력 | 음성(SuperWhisper 등)으로 **“사이드바 패딩 반으로”** 처럼 말하기 |
| 수락 | **Accept All**, diff **안 읽음** |
| 디버깅 | 에러 로그 **복사만** 해서 넣기 — 설명 없이도 고쳐지는 경우 많음 |
| 한계 | 버그가 안 고쳐지면 **우회**하거나 랜덤 변경 요청 |
| 체감 | 코드가 **이해 범위를 넘어감** — 읽으려면 시간이 듦 |

“코딩이 아니다 — **보고, 말하고, 실행하고, 붙여 넣고**, 대부분 된다”는 표현이 핵심이다.

---

## 3. 바이브 코딩 vs AI 보조 코딩

**모든 AI 코딩이 바이브 코딩은 아니다.** 개발자 사이에서 자주 쓰는 구분:

| | 바이브 코딩 (극단) | AI 보조 코딩 (실무에 가까움) |
|--|-------------------|------------------------------|
| 코드 이해 | **의도적으로 안 읽음** | 생성 후 **읽고·테스트** |
| diff | 전부 수락 | **줄 단위 검토** |
| 디버깅 | 에러 붙여 넣기 위주 | 원인 추적 + AI 제안 **검증** |
| 적합 | 프로토타입·개인 실험 | 기능 추가·리팩터·위키 초안 |
| 위험 | 보안·유지보수·버그 은폐 | 낮추려 해도 **여전히 검수 필요** |

```text
AI가 한 줄이라도 썼다
 ├─ diff 읽고 이해했다 → AI 보조 (Willison 등이 말하는 “타이핑 도우미”)
 └─ diff 안 읽고 믿었다 → 바이브 코딩
```

[[Cursor 사용법]] §8 **diff 읽고 수락**은 **바이브 코딩의 반대편** 습관이다.

## 4. 잘 맞는 경우

| 상황 | 이유 |
|------|------|
| **주말·1회성** 웹앱·데모 | 버려도 됨 |
| **아이디어 검증** | 속도가 가치 |
| **UI·레이아웃** 시안 | “느낌”이 목표 |
| **비개발자**가 자기용 도구 | 코드를 몰라도 **결과**만 필요 |
| **스크립트·자동화** 초안 | 나중에 정리할 여지가 있을 때 |
| **공개 위키** 초안 | 표기·면책 규칙으로 **사람이 다시 읽음** — [[Obsidian 사용법]] |

[[LLM Wiki]]처럼 raw→위키 자동화와도 **겹치는 면**이 있지만, 공개 글은 **사람 검수·규칙**을 전제로 한다.

---

## 5. 위험한 경우

| 상황 | 위험 |
|------|------|
| **결제·개인정보·의료·금융** | 유출·규제·오정보. 건강·금융 안내는 **면책·사실을 사람이 검수** |
| **장기 운영** 서비스 | 이해 못 한 코드는 **수정·장애 대응** 불가 |
| **팀 협업** | 스타일·아키텍처 불일치 |
| **오픈소스·라이선스** | AI가 **출처 불명** 코드를 섞을 수 있음 |
| **`.env`·키·토큰** | 채팅에 넣으면 유출 — [[Cursor 사용법]] §12 |
| **운영 명령** | `git push --force`, `rm -rf` 등 **에이전트 실행** 무비판 수락 |

마틴 파울러(Martin Fowler) 등도 **유지보수·정확성·보안** 문제로 **일회용·소규모**에 한정하라고 정리했다.

---

## 6. 흔한 문제

| 문제 | 설명 |
|------|------|
| **환각 API** | 없는 함수·잘못된 패키지 이름 |
| **겉만 동작** | 해피 패스만 되고 엣지 케이스 붕괴 |
| **보안 구멍** | SQL injection, XSS, 하드코딩 비밀 |
| **기술 부채** | 구조 없이 기능만 쌓임 — [[디자인 패턴]]·레이어 무시 |
| **스킬 퇴화** | 읽지 않으면 **디버깅·설계** 능력이 안 늘음 |
| **우회 누적** | “일단 되게” 패치가 쌓여 **원인 불명** 버그 |

“컴파일/실행되면 끝”은 **프로덕션**에서는 거의 항상 부족하다.

---

## 7. 바이브에 가깝게 쓰되 덜 망치기

완전 검수형이 아니어도, **최소 안전장치**는 둔다.

| 단계 | 할 일 |
|------|------|
| 범위 | **작게** — 한 번에 파일·기능 수 제한 |
| 비밀 | 키·토큰·환자정보 **프롬프트 금지** |
| 실행 | 터미널 명령은 **읽고** 허용 — [[Cursor 사용법]] §9 |
| 핵심만 | 결제·인증·삭제 경로는 **손으로** 또는 diff 집중 검토 |
| 테스트 | 자동 테스트·수동 시나리오 **한 번** |
| 커밋 | 큰 덩어리보다 **작은 커밋** — 되돌리기 쉽게 ([[Git 사용법]]) |
| 위키 | 면책·사실·표기 — **사람이 최종 읽기** |

```text
바이브로 속도 ↑  +  위험 구간만 사람 검수  =  실무에서 흔한 절충
```

## 8. 도구별 (방향만)

| 도구 | 바이브에 가까운 쓰임 |
|------|---------------------|
| [[Cursor 사용법]] Agent | “만들어줘” + Accept All — **가장 자주 언급** |
| ChatGPT·Claude 채팅 | 코드 블록 복붙, 설명 없이 실행 |
| [[GitHub Copilot 사용법]] Tab | 제안을 **읽지 않고** 연타 수락 |
| Replit·Bolt 등 | 브라우저에서 **전체 앱** 생성 |
| [[Lovable 사용법]] | 말로 풀스택 웹앱·배포. 한글명 **러버블** |

도구를 바꿔도 **“검수 없음”**이면 같은 위험이다. [[현존 AI 비교]]에서 역할을 나눈다.

---

## 9. 위키 글을 쓸 때

| | 바이브에 가깝게 | 검수형 |
|--|----------------|--------|
| 초안 | Agent에 “글 써줘” | 기존 글·규칙을 `@`로 첨부 |
| 검수 | 생략 | **diff 읽기**, 표기·면책·목차 |
| 배포 | 초안 그대로 | 공개 플래그·빌드 설정을 확인 — [[Quartz 사용법]] |
| 건강·금융 | — | **강한 면책**, 자가 진단 금지 |

위키는 **바이브로 쓰고 사람으로 고치는** 반자동이 현실적이다. [[Cursor 스킬 설정]]·에디터 규칙이 “바이브의 가드레일” 역할을 한다.

---

## 10. 실전 체크

- [ ] **버릴 수 있는** 범위인가 (프로덕션·개인정보 아님)  
- [ ] diff를 **전혀** 안 읽어도 되는지, 아니면 **일부만**이라도 읽을지 정했는가  
- [ ] 에러를 붙여 넣기만 하지 않고, **재현 조건**을 한 줄이라도 적었는가  
- [ ] 비밀·`.env`를 채팅에 넣지 않았는가  
- [ ] 터미널 **위험 명령**을 막았는가  
- [ ] 나중에 **내가 고칠 수 있는** 크기인가

## 11. 정리

| 항목 | 한 줄 |
|------|--------|
| 정의 | AI에 **코딩을 맡기고**, 극단형은 **코드를 읽지 않음** |
| 유래 | 카파시 **2025**, Cursor·음성 입력 예시 |
| 장점 | **속도·접근성·프로토타입** |
| 단점 | **보안·유지보수·이해 부족** |
| 실무 | 도구는 [[Cursor 사용법]] 등과 같고, **검수 유무**가 갈림 |

## 면책

> **면책**  
> - “바이브만 하면 된다”는 **권유가 아니다.** 회사·법규·보안 정책이 우선.  
> - AI 생성 코드·문서는 **오류·유출·라이선스** 위험이 있다.  
> - 의료·금융·법률 내용은 AI 초안만으로 **공개·의사결정**하지 않는다.
