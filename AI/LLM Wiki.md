# LLM Wiki

> **분류:** AI · [[생활위키 목차]]

**LLM Wiki**는 LLM이 **원본 자료를 한 번 읽고**, 요약·개념 페이지·교차 링크가 있는 **마크다운 위키를 유지**하게 하는 지식 관리 패턴이다. 
질문할 때마다 PDF를 처음부터 다시 뜯는 **RAG**(검색 증강 생성)와 달리, **미리 정리된 위키 층**을 읽고 답하는 쪽에 가깝다.

안드레이 카파시(Andrej Karpathy)가 소개한 흐름이 널리 퍼졌고, Microsoft는 VS Code 확장 **[llmwiki](https://github.com/microsoft/llmwiki)** 로 비슷한 워크플로를 제공한다.

이 글은 **개념·RAG 비교·이 생활위키와의 차이**를 정리한다. 특정 제품 설치 매뉴얼 전체는 아니다.

확인일: 2026-08-11

관련: [[현존 AI 비교]] · [[NotebookLM 사용법]] · [[Obsidian 사용법]] · [[Cursor 사용법]]

---

## 1. 개요

| 항목 | 설명 |
|------|------|
| 무엇 | LLM이 **위키 레이어**(`.md` 페이지 묶음)를 **작성·갱신**하고, 사람은 소스를 넣고 질문한다 |
| 핵심 아이디어 | 비싼 **통합·요약·링크** 작업을 **ingest(넣을 때)** 에 하고, 질의 때는 **정리된 위키**를 본다 |
| 원본 | **raw** 폴더 등 — 사람이 넣은 PDF·노트. LLM이 **수정하지 않는** 근거 |
| 위키 | **wiki** 폴더 — 개념·엔티티·색인 페이지. `[[위키링크]]`로 연결 |
| 규칙 | **스키마** — `AGENTS.md`·`CLAUDE.md` 등에 구조·형식·워크플로 정의 |
| 반대 개념 | 매 질문마다 청크 검색만 하는 **상태 없는 RAG** |

“LLM + 위키”라고 해서 **사람이 쓰는 위키에 AI를 붙인 것**과 **AI가 위키 전체를 유지하는 것**은 다르다. 아래 §6 참고.

## 2. RAG·NotebookLM·LLM Wiki 비교

```text
RAG
 질문 → 원문 청크 검색 → LLM이 그 자리에서 합성 → (결과 버림)

NotebookLM
 소스 업로드 → 채팅·스튜디오에서 그라운딩 Q&A → (노트북 안에서 유지)

LLM Wiki
 소스 ingest → LLM이 위키 페이지 작성·갱신 → 질문 시 위키를 먼저 읽음
```

| | RAG | [[NotebookLM 사용법]] | LLM Wiki |
|--|-----|----------------------|----------|
| 저장 형태 | 벡터 DB·청크 | 클라우드 노트북·소스 | 로컬 **마크다운 위키** |
| 지식 정리 | 질의 때마다 재검색 | 소스 기반 Q&A·오디오 등 | **ingest 때** 페이지·링크 생성 |
| 교차 연결 | 약함 (청크 단위) | 노트북 내 비교 | `[[링크]]`·색인·개념 페이지 |
| 규모 | 대량·자주 바뀌는 문서에 유리 | 주제별 노트북 | **수십~수백 개** 큐레이션 코퍼스 |
| 인용 | 청크 단위 추적 가능 | 소스 인용 강함 | 위키 → raw **2단계** (해석이 끼일 수 있음) |
| 환각 | 답 1회에 국한되는 경우 많음 | 그라운딩으로 완화 | ingest 때 **위키에 굳어질 위험** |

세 가지는 **배타적이 아니다.** 연구 프로젝트는 LLM Wiki로 정리하고, 긴 꼬리 검색은 RAG를 붙이는 **하이브리드**도 흔하다.

## 3. 세 층 구조 (카파시·llmwiki 패턴)

| 층 | 소유 | 역할 |
|----|------|------|
| **Raw Sources** | 사람 | PDF·기사·메모 원본. **불변** 근거 |
| **Wiki** | LLM (사람 검수) | 요약·개념·엔티티·비교·색인 `.md` |
| **Schema** | 사람 + LLM | 폴더 규칙, 페이지 형식, ingest·질의 절차 |

```text
새 PDF·노트 추가 (raw/)
 ↓
LLM ingest: 핵심 추출, 기존 페이지 갱신, 모순 표시, [[링크]] 추가
 ↓
wiki/ 색인·개념 페이지 갱신
 ↓
질문: 위키 색인 → 관련 페이지 → 필요 시 raw 인용
 ↓
output/ (선택) 보고서·답변 초안
```

스키마 예시에 넣는 내용:

- 페이지마다 **상단 요약**·**출처 표기**
- 개념마다 **관련 링크** 최소 N개
- raw는 **읽기만**, wiki만 LLM이 쓴다
- 질의 시 **위키 우선**, 모르면 “근거 없음”

---

## 4. ingest vs 질의

| 시점 | 하는 일 | 비용·품질 |
|------|---------|-----------|
| **Ingest** | 읽기·요약·분류·교차 참조·색인 갱신 | **무겁다** (긴 문맥·추론). 한 번 잘못 쓰이면 위키 전체에 퍼질 수 있음 |
| **질의** | 색인·관련 페이지 읽고 합성 | RAG가 raw 청크만 읽는 것보다 **가벼운 편**일 수 있음. 그래도 합성은 필요 |

**복리 효과:** 같은 주제 소스가 50개 쌓이면, 미리 엮인 위키가 **관계·모순**을 담고 있어 “다섯 글을 연결하는 질문”에 유리하다는 설명이 많다.  
반대로 ingest 품질이 나쁘면 **잘못된 요약이 링크로 전파**된다 — RAG보다 **되돌리기 어렵다**는 비판이 있다.

## 5. 언제 쓰나

| 잘 맞는 경우 | 덜 맞는 경우 |
|--------------|--------------|
| 논문·강의·책 **한 주제** 깊게 | 수백만 건 고객 문서 **실시간 검색** |
| 개인 연구 노트·저널 **장기 축적** | 출처 한 줄 단위 **법무·감사** (raw 청크 RAG가 나을 수 있음) |
| 개념 간 **관계·타임라인**이 중요 | 소스가 **매시간** 갱신 |
| 로컬 **마크다운 소유**가 중요 | 설치 없이 **브라우저만** — [[NotebookLM 사용법]] 쪽 |

Microsoft **llmwiki** 확장은 VS Code 안에서 ingest·검색·질의 명령을 제공한다. Cursor·[[Cursor 사용법]]과 같이 **에디터 + LLM** 환경과 겹친다.

## 6. 이 생활위키와의 관계

**생활위키**는 LLM Wiki **패턴 그 자체가 아니다.**

| | LLM Wiki (패턴) | 이 vault (생활위키) |
|--|----------------|---------------------|
| 위키 글 작성 | LLM이 **유지** (사람은 소스·규칙) | 사람이 **직접 쓰거나** [[Cursor 사용법]]으로 초안·수정 |
| 품질 통제 | 스키마 + 검수. 안 하면 AI 해석이 굳음 | [[공개 규칙]]·면책·한글 표기 규칙 등 **사람 규칙** |
| 링크 | LLM이 ingest 때 생성 | `[[생활위키 목차]]`·분류 폴더·수동 링크 |
| 공개 | 로컬·별도 vault | Quartz로 **선별 공개** (`publish: true`) |
| 용도 | 연구용 **컴파일된** 지식 베이스 | 생활·도구·건강 등 **검수된** 위키 |

```text
생활위키 실무 (현재)
 Cursor Agent + 규칙(.cursor/rules) + 사람 diff 검수
 → 사람이 소유한 위키 (AI는 보조)

순수 LLM Wiki
 raw 추가 → LLM ingest가 wiki 전부 갱신
 → AI가 유지하는 위키 층 (사람은 소스·스키마)
```

LLM Wiki를 **테스트**할 때는 **별도 폴더·vault**를 두는 것이 안전하다. 기존 위키와 **섞으면** “내가 쓴 글”과 “모델이 추론한 글” 경계가 흐려진다는 지적이 있다 ([InfraNodus 등](https://infranodus.com/about/rag-vs-llm-wiki)).

**함께 쓰는 예:**

1. 주제 조사 — [[NotebookLM 사용법]] 또는 Perplexity로 사실 확인 ([[현존 AI 비교]])  
2. 글화 — [[Cursor 사용법]]으로 `생활-건강/` 등에 **사람 검수** 초안  
3. 연구 전용 — 다른 디렉터리에서 LLM Wiki로 raw→wiki 컴파일 후, **필요한 부분만** 수동 반영

## 7. 도구·스킬 (참고)

| 이름 | 설명 |
|------|------|
| **[microsoft/llmwiki](https://github.com/microsoft/llmwiki)** | VS Code 확장. 폴더 ingest, 위키 검색, 질의 |
| **Karpathy 스캐폴드** | `raw/` · `wiki/` · 스키마 md. 커뮤니티 스킬·가이드 다수 |
| **InfraNodus LLM Wiki skill** | 위키 + 지식 그래프 등 (상용·스킬 생태계) |
| **[[Obsidian 사용법]]** | LLM Wiki **결과물**을 읽기·수정하기 좋은 뷰어. 패턴 자체는 아님 |
| **[[Cursor 사용법]]** | 스키마·규칙을 `.cursor/rules`·스킬로 두고 **반자동** 위키 작성 |

“LLM Wiki”라는 이름의 **제품 하나**라기보다, 위 도구들이 구현하는 **아키텍처 이름**에 가깝다.

## 8. 장점 / 한계

| 장점 | 한계 |
|------|------|
| ingest 후 **세션 넘어** 합성·링크 유지 | 잘못된 요약이 **여러 페이지에 전파** |
| 주제 **깊이·연결** 질문에 유리 | 대규모·실시간 코퍼스엔 RAG가 나을 수 있음 |
| **로컬 md** 소유 | ingest·갱신에 **토큰·시간** 소모 |
| 사람이 읽을 수 있는 **중간 산출물** | raw와 wiki **이중 관리** |
| 스키마로 형식 **강제** 가능 | 스키마 없으면 위키가 **난잡해짐** |

---

## 9. 시작할 때 체크

- [ ] **별도 폴더**인가 (기존 개인 위키와 분리)  
- [ ] `raw/`는 **읽기 전용** 규칙이 있는가  
- [ ] wiki 페이지에 **출처·날짜**를 남기는가  
- [ ] ingest 후 **사람이 샘플 검수**하는가  
- [ ] 환각·모순 시 **raw로 되돌아가는** 절차가 있는가  
- [ ] 민감·의료·금융 결정을 **위키만**으로 하지 않는가  

---

## 10. 정리

| 항목 | 한 줄 |
|------|--------|
| 정의 | LLM이 **마크다운 위키를 유지**하고, 질의는 그 위키를 읽는 패턴 |
| RAG와 | RAG는 **질의 때 검색**, LLM Wiki는 **ingest 때 컴파일** |
| NotebookLM과 | 노트북 Q&A vs **파일 기반 위키 레이어** |
| 생활위키와 | 여기는 **사람 주도 위키 + Cursor 보조**. 순수 LLM Wiki와 구분 |
| 주의 | **별도 vault**, ingest 검수, 굳은 환각 |

---

## 면책

> **면책**  
> LLM Wiki·RAG·도구 이름·기능은 **빠르게 바뀐다.** 공식 README·릴리스 노트를 본다.  
> AI가 만든 위키 내용은 **사실이 아닐 수 있다.** 의료·법률·금융·투자 결정에 쓰지 않는다.  
> raw에 **비밀·개인정보**를 넣으면 LLM·로그 정책에 따라 유출 위험이 있다.  
> 이 글은 패턴 설명이며 특정 확장·스킬의 전체 매뉴얼이 아니다.
